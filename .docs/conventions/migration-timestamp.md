# Convention — Millisecond Timestamps for Migrations (org-wide)

Migration naming rule that applies to **all** repos in the org that use schema versioning (TypeORM, Knex, Sequelize, Flyway, or any custom runner).

---

## 1. 🔒 New migrations use millisecond timestamps, never sequential increments

When generating or creating a migration, the name prefix must be the **Unix timestamp in milliseconds** at the moment of creation — never `001`, `002`, nor the next number after the last existing file.

**Correct form:**

```
1749998400000_add_speaker_status_enum.ts
1750001200000_create_activity_instructors.ts
```

**Forbidden form:**

```
001_add_speaker_status_enum.ts          ← sequential number
0042_create_activity_instructors.ts     ← manual increment from last
```

Getting the creation timestamp:

```bash
node -e "console.log(Date.now())"
# or
date +%s%3N          # Linux/macOS/Git Bash
```

Frameworks with native generators (TypeORM `migration:generate`, Knex `migrate:make` with `--timestamp` option) already produce the timestamp — do not manually override it with a sequential number.

---

## 2. Why not just seconds (without ms)?

Second-precision timestamps (`1749998400`) collide when two deploys or two developers generate migrations in the same second — rare but real in simultaneous CI + local runs. Milliseconds reduce collision to zero in practice and are the format already used by TypeORM/Knex generators by default.

---

## 3. Resolving conflicts between branches

If two branches add migrations with close timestamps, **do not renumber** — the timestamp is already the application order. Just ensure the runner applies them in ascending name order (default behavior of all listed runners). There is no real merge conflict: files have distinct names and the runner applies both in sequence.

If the project's runner uses a control table (`migrations` / `schema_migrations`), confirm that the primary key is the full filename (or the extracted timestamp), never a local auto-increment.

---

## 4. Accepted exceptions (with justification)

| Situation | Accepted | Condition |
|---|---|---|
| Seed / local fixture migration (no deployment) | sequential OK | File outside the canonical `migrations/` directory |
| Legacy runner that only accepts short integers | sequential OK | PR comment explaining the runner constraint |
| Migration generated by a 3rd-party CLI (Prisma `migrate dev`) | CLI format | Do not alter the generated name |

Every exception must have a one-line justification in the PR or the file header.

**Why:** the root of the problem is branch parallelism — two developers working on different features create `0043_foo.ts` and `0043_bar.ts` in the same repo, causing a number conflict and ordering ambiguity. Millisecond timestamps are unique by construction, require no inter-branch communication, and are the standard already adopted by canonical generators. Zero adoption cost, zero collision in practice.
